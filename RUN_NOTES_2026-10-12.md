## LLM arm: where the rejections come from

The dominant cost is the **independent dual reader acting as an AND-gate** (`--llm-dual-read gate`,
the default): 721 of ~980 gate failures, agreement only 47.5%. Most disagreements are annotation-level
rather than meaning-level — e.g. it reads `ASK_KB(intent=window_check)` / `count_options` where the base
card says something else, or adds `corrected_from=...` when a `self_correction=false_start` factor made
the text look like a repair. The deterministic rule reader accounted for 196 failures, mostly KB-intent
cue loss when the writer paraphrases ("how far back can you check" → "tell me days").

A re-run with `--llm-dual-read report` should raise materialisation substantially at near-zero API cost,
because generations are content-addressed and cached.

API usage: 3,025 calls, 0 errors, ~2.66 M input / 115 k output tokens (~$1 at `deepseek-chat` prices).

## Windows-only issues (locale codec) — not fixed in this branch

About 30 file operations use the platform locale codec instead of UTF-8. On Linux/Colab the locale *is*
UTF-8 so nothing shows; on Windows (cp1252) three things break:

1. **`gmsjourney/pipeline.py:117`** — the store cache key hashes `Path(policy_path).read_text()`.
   `policy/charge_review_kg.json` is UTF-8; decoded as cp1252 it silently becomes mojibake, so the key —
   and the trained store — depend on the machine locale. (Observed as an unexpected full store rebuild.)
2. **`gmsjourney/pipeline.py:446`** — `report.html` contains `φ` (U+03C6); `write_text` raises
   `UnicodeEncodeError` on the final write, losing the report after a complete run.
3. **`gmsjourney/knowledge/kx_store.py:135`, `ingest.py:148`, `policy_kg.py:477`** (encoder corpus and
   policy ingestion) and the dataset CSV writers / `gms_canonicals.json` — same pattern.

Workaround used here: `PYTHONUTF8=1`. Proper fix: pass `encoding="utf-8"` at those call sites (or read
bytes and decode), or document UTF-8 mode for Windows.
