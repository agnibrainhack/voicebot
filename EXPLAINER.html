Inside gmsjourney

What every step of this pipeline does, with the real files it reads and writes — illustrated with data from the end-to-end run on your machine.

This page assumes you have never read a line of this code. It starts from the idea, then walks the twelve steps in order. Each step answers four questions: what comes in, which function does the work, what happens inside, and what comes out. Every number and every snippet below is copied from the run in campaign_llm/, so you can open the files and see them yourself.

The whole thing in one analogy

Imagine a bank has a phone robot that handles “I don’t recognise this charge on my card” calls. The bank also has a written procedure: a rulebook that says what the robot may ask, what it may promise, how many times a customer may retry their card digits, how far back charges can be reviewed, and so on.

Before letting that robot talk to real customers, you want evidence. Not “we tried a few calls and it seemed fine” — actual evidence, at scale, that says: here are 500 realistic conversations, here is what the correct answer was for each one and why, and here is exactly how the robot did.

This program is the machine that produces that evidence. It is a test factory, and its raw material is the rulebook itself:

  1. It shreds the procedure document into index cards (the policy graph).
  2. It teaches a “memory” those cards so questions can be checked for truth (the GMS store).
  3. It manufactures hundreds of customer conversations from the rulebook — every rule, every boundary, every failure path (the bases).
  4. It dresses each conversation in realistic human messiness: typos, fillers, rambling asides, urgency (enrichment).
  5. Before running anything, it proves that the messy version still means exactly what the clean version meant (the invariance proof). This is what makes the results trustworthy: if a test fails, it is the robot’s fault, not a badly written test.
  6. It runs the robot through every conversation while a supervisor watches each sentence and each tool call live (the runtime monitor).
  7. It reports what broke, which kind of messiness caused it, and whether the test suite itself is strong enough to catch deliberately broken robots (diagnosis, mutation, resilience).

There are two ways the messy conversations get written. The template arm writes them with deterministic code — always available, always reproducible. The LLM arm (your DeepSeek run) asks a language model to write them like a real person would, and then checks the model’s work much more strictly, because a model can quietly change the meaning of a sentence.

00Compile the rulebook into a graph
Analogy: shredding a policy document into index cards. Each card says one thing, and — this is the important part — every card can be traced back to the exact sentence and page it came from. Nothing is paraphrased, nothing is invented, and nothing is “remembered” from someone’s summary.

fictional_poc_operating_procedure_gpt_readable.pdf — the bank’s procedure, plus gmsjourney/policy/charge_review_policy.md, a structured transcription of it.

The call

Validating an existing file: … policy_kg check

01Train the GMS store
Analogy: hiring a librarian who memorises every card, then testing whether they flinch at forgeries. You don’t just want a lookup table — you want someone who can be shown a plausible but false card (“the fee is $150”) and answer “that doesn’t fit what I know, the distance is too large.” That distance is the whole trick: it turns “is this true?” into geometry.

Input

charge_review_kg.json → rendered into policy.gms.md, one table per relation.

The call

build_gms(policy_path, backend_choice="auto", epochs=150, geode_epochs=80, seed=42, dedup_mode="off", v_sft_mode="ab")

With knowlytix installed and licensed this delegates to build_kx_store(); otherwise the built-in fallback builds an equivalent store.

Output (your run)

  • 231 entities, 609 triples, 12 exact numbers
  • GEODE converged in 1 iteration (895 proposed, 609 kept)
  • 14 anchor violations reported — e.g. ack_declined pointing at two different rules
  • Store directory: ~/.cache/gmsjourney/stores/<hash>/, with kx/model.pt and gms_build_report.json

The trained store is the single most reused artifact in the pipeline: seven later steps ask it questions. It is also cached by a hash of its inputs, so a second run reloads it in about two and a half minutes instead of rebuilding for half an hour.

02Write the exam questions
Analogy: a teacher writing questions and marking their own paper twice by different routes. A question is only used if the answer can be re-derived symbolically (from the rule) and confirmed geometrically (the store places it inside the tolerance). Questions that pass both are “admitted”; the ones that can’t are still kept, but labelled with the reason, so nothing is silently dropped.

Input

The trained store, plus the 18-category question taxonomy.

The call

mine_kb_items(store, seed=42) # each item admitted by two_way_check(store, truth, seed=7)

Output (your run)

  • 31 policy questions, each with its answer computed from the store
  • 4 hallucination probes — 3 “near-miss” option names that don’t exist in the policy, and 1 unstated fee. The correct answer for all four is “that doesn’t exist”, so a bot that invents an answer is caught.
  • Written into dataset/policy_questions.csv and the bases inside report.json

A real question with its provenance

question : "How much does standard delivery cost?" card : ASK_KB(intent=value, attr=fee, entity=standard_delivery) answer : 0 ← read from exact memory (T0027), never from prose admission: two_way ← symbolic re-derivation + inside the calibrated tolerance

The graph answering its own questions is a precondition, not a result: if the store can’t answer its own exam, the exam is broken. In your run it answered 100%.

03Build the journey test matrix
Analogy: crash-testing cars without building every possible car. Instead of the millions of combinations, you pick a small set that still covers every pair of features (a “covering array”), then add special cases until every rule, every workflow edge, every escalation trigger and every boundary has been exercised at least once (“closure”). It’s how testers get most of the coverage for a fraction of the runs.

Input

13 content dimensions — authentication path, retrieval, number of transactions, 30-day window, disposition pattern, record result, card intent, options availability, confirmation, submit result, human request, mid-journey question, turn pressure.

The call

gen = JourneyBaseGenerator(oracle, kb_pool, seed=42) cover, report = gen.covering() # 50 journeys extra = gen.closure(cover, store, report, extra_traces=kb_traces) item = to_item(spec, oracle, "J000")

Output (your run)

  • 54 journey bases + 31 policy questions = 85 bases
  • Level pairs covered: 523 / 523 (276 pairs are impossible by construction and recorded as such, not dropped)
  • Every rule R1–R30, every workflow edge and every trigger exercised
  • Each base carries: the exact conversation text, the meaning card per turn, the oracle’s tool calls, and the expected verdict

Two ideas make the base honest. First, relevance collapse: after a failed authentication, everything downstream is marked N/A — a pair only counts as “covered” when both halves could actually matter. Second, the oracle plays the conversation for real against the same mock bank the bot will face, so the expected verdict is computed, never hand-written.

04Choose the knobs and the schedule
Analogy: deciding which dials to twiddle on the test rig (background noise? accent? rambling?) and writing a fair schedule so each dial setting gets spread evenly across cases instead of clustering. Without this, a failure could just mean “this case also happened to be the noisy one”.

Input

The 42-factor catalog from proofloop, plus an application layer that selects 16 factors that make sense for a phone call and records the other 26 with a reason for exclusion.

cat = Catalog.load() suite = resolve_profile(cat, "voice_full") rows = compose(suite.level_specs(), bases, n_runs, seed, mode="embedded", assign="dispersed")

Output (your run)

  • 85 design rows — one messy variant per base at this scale (the README’s published run uses six per base)
  • Factors include noise (none/typo/asr), disfluency, style, numeric_format (digits/spoken), entity_aliasing, paraphrase_depth, question_format, emotional_frame, self_correction, history, instruction_conflict, answer_anchoring, confidence_pressure, clarity, specificity, length
  • The design quality (φp fill, power curve, and knowlytix’s own DesignMatrix for comparison) lands in report.json → design

The rule that governs this step: any dial that could change the correct answer is not a dial — it is part of the base. For example, a failed tool means the bot must transfer, and an ambiguous answer means the bot must ask for clarification. Those aren’t “variation”; they change what’s correct, so they live in the base and the catalogue records them as moved_to_base.

05Prove the messy tests are the same tests
Analogy: you re-record the same sentence with a bad phone line, a heavy accent and someone rambling about their morning — and then you prove, with a listener, that all three recordings still mean exactly the same thing. If you skipped this, a failure could just as easily mean “the test was garbled” as “the robot misunderstood”. This proof is what makes every later number mean something.

The call

realizer = Realizer() reader = FrameReader(store) validator = InvarianceValidator(store, oracle, reader, realizer) proof = validator.prove(scenario) controls = validator.negative_controls( scenarios, per_type=40)

Output (your run)

  • 85 / 85 scenarios proved, across 754 customer turns, zero re-seeds
  • Maximum frame distance among accepted turns: 0.0 — every read-back card identical to the intended one
  • Negative controls: 433 / 433 meaning-changing edits rejected across 20 kinds (negation flips, digit swaps, wrong dialog state, an inserted turn…)
  • Evidence exported as RDF in ontology.ttl; per-turn detail in dataset/test_turns.csv

The four layers, in plain words

LayerClaimHow it’s checked
L1The correct answer didn’t drift between generating and running the test.Hash of the carried ground truth equals a freshly recomputed one.
L2Each messy turn still means what the clean turn meant.The reader turns the messy text back into a meaning card; it must equal the intended card in that dialog state.
L3The conclusion survives re-derivation.The oracle replays the read-back cards end to end and must reach the same outcome and per-stage decisions.
L4Reported, not gating.How far the surface text moved (cosine) — evidence that the variation is real, not a claim of correctness.

The controls are the part that keeps the proof honest. A checker that accepts everything would pass L1–L3 trivially; so the same machinery is fed edits that must change the meaning, and every one of them must be rejected. In your run all 433 were — including 40 “wrong dialog state” edits, where the same words are answered in a state that reads them differently.

05bLet DeepSeek write them instead
Analogy: the template arm is a scriptwriter following a formula. The LLM arm is a freelance writer with better instincts and no loyalty to the formula — so you hire them, but you never let them see the answer key, and every sentence they write goes past a bouncer before it reaches the robot. Sentences that pass are pinned: the robot later receives exactly the text that was proved, not a fresh generation.

The call

settings = LLMSettings(model="deepseek-chat", temperature=0.7, mode="live") realizer, validator, clients = build_llm_arm( store, oracle, reader, validator, settings, dual_read="gate", adversarial=True, max_attempts=3)

Blind generation: the prompt (enrich/llm/prompts.py) contains the agent’s question, the meaning in plain words, the base wording and the style instructions — never the expected behaviour, the tools or the rule ids.

Output (your run)

  • 29 / 85 scenarios materialised (34%); 754 turns; 54.8% accepted on the first attempt; 1.82 attempts per turn
  • 3,025 DeepSeek calls, 0 errors, ~2.66M input / 115k output tokens
  • Controls on the model’s own text: 95 / 96 rejected; adversarial rewrites 20 / 20 rejected
  • Every turn recorded in dataset/llm_enrichment_turns.csv

The gates each sentence must pass

GateQuestion it asksExample of a failure
G0 formIs this one spoken line, with no speaker labels, stage directions or internal names?“Customer: yes, record_charge_response it”
G1 factsDid it invent a number, a fee or a merchant that the base meaning doesn’t carry — and did it keep every value it must?“…I heard it’s ten dollars” when $10 is nowhere in the case
G3 one decisionIs there exactly one clear decision, with no competing cues (unless a self-correction was requested)?“I recognize it, it’s not mine.”
G2 meaningDoes the deterministic reader, reading the noisy final text in its dialog state, recover the intended card?“Uh, days?” for a question that must mean limit/lookback_days
G2′ dual readDoes an independent LLM reader, which never saw the base, recover the same card?It reads ASK_KB(intent=count_options) where the base is intent=limit

When a gate fails, the turn is regenerated with feedback that names the failed gate and nothing else (“the independent reader recovers a different meaning: …”). After three attempts a scenario is declared not materialised and excluded from the arm’s results — reported, never silently dropped.

ACCEPTED — state ASK_AUTH, meaning PROVIDE_CREDENTIAL(credential=4821) base : The last four digits of my card are 4821. llm_final : Hey, it's probably nothing, but the last four digits of my card are — sorry, the last four digits of my card are four eight two one. That second example is the dominant failure mode of the whole arm — 721 of ~980 gate failures came from the independent reader, with only 47.5% agreement. Many are annotation disagreements rather than real misunderstandings, which is why a re-run with --llm-dual-read report (agreement measured but not gating) is the cheap next experiment: the generations are cached, so it costs minutes, not hours.

06Set the smoke detector’s sensitivity
Analogy: a smoke detector that’s too sensitive goes off when you make toast (false alarms, and everyone ignores it); too dull and it misses a fire (a bad tool call sails through). This step picks the threshold from data — the strictest setting that produces zero false admits, then the fewest false rejects.

The call

cal = calibrate_plausibility(store) pc = calibrate_plan(store, journeys) gcfg = GovernanceConfig( theta=cal["theta"], drift_budget=pc["drift_budget"], plan_criterion=pc["criterion"], decision_rule="strict") # or "quorum"

Output (your run)

  • Plausibility threshold θ = 0.9591 at the regulated operating point: 0 false admits, 0 false rejects
  • Reported alongside: gmsh’s P=0.5 point (θ = 0.917), held-out accuracy, and bootstrap 95% intervals
  • A probe sweep (known-good and known-bad transitions) and the multi-threshold design land in report.json → governance

The monitor is not one check but a stack, each with its own sensitivity: a syntax gate, ten symbolic policy rules (authenticate before account tools, no claim without a success status, disclose the $15 fee before confirming…), the geometric plausibility gate above, a plan gate on the whole trajectory, a speech monitor, and a numeric attestor that grades every figure the bot says as PASS / REVIEW / FAIL. A quorum mode is also computed in shadow: one blocking layer routes to human review instead of denying outright.

07Run the bot under supervision
Analogy: the exam itself. A fresh robot and a fresh fake bank for every single case (so nothing leaks between tests), a simulated customer who answers whatever the robot actually asks, and an invigilator watching every move as it happens — not afterwards.

The call

Swap in your own bot with CallableBotAdapter or HTTPBotAdapter; the same monitor wraps it.

Output (your run)

  • Base cases: 90.6% correct, workflow adherence 100%, KB answers 84.6%
  • Enriched (template): 49.4% — the messiness costs ~41 points
  • Enriched (LLM arm): 58.6% on the 29 materialised cases
  • Runtime monitor: 0% false alarms on correct runs; 13 of 53 failed runs flagged live
  • Written to results_enriched.csv, failures.jsonl, dataset/turn_by_turn.csv

The verdict for each case has three independent parts: the outcome (end state, transfer reason, what was really recorded), each stage’s decision (authenticate, retrieve, present, capture, record, card action, transfer, summary), and admissibility (was every step allowed — no tool before login, no promise without success, no submit before confirmation and fee disclosure, no run past 20 turns). A bot may take a different but legal route and still pass: the grading is on decisions and tool calls, not on wording — which is exactly why the turn-by-turn view exists alongside it.

08Detective work: which knob broke it?
Analogy: you know 43 of 85 runs failed. But why? This step is a statistician looking for the dial settings that keep showing up in failures — and then correcting for the fact that you tested many dials at once, so one of them would look guilty by luck alone.

The call

attribution.diagnose(rows, factor_names) kx_attribution(rows, factor_names) # knowlytix DOE

Output (your run)

  • Worst levels: disfluency=fillers (72% failure rate), noise=asr (68%), numeric_format=spoken (65%), style=formal (61%)
  • disfluency is the strongest factor (deviance 11.3, pseudo-R² 0.10) but after correcting for multiple comparisons it sits just outside significance (padj = 0.051)
  • Weakest link by stage: KB retrieval (19) then authentication (18)

Read the caveat with the number: this run has 85 rows, so the confidence intervals are wide (the honest Wilson intervals are in the report next to each rate). The pattern — telephone-style noise and spoken numbers cost the most — matches the published full-scale run, which had 486 rows and much tighter intervals.

Silent failure is the dangerous one.

Output (your run)

10Hire 17 impostors
Analogy: how do you know your exam is hard enough to catch a bad employee? You build 17 fake employees, each with exactly one flaw — one reviews 5 transactions instead of 4, one claims success before the system confirms it, one fabricates an answer instead of saying “I don’t know” — and check whether the exam catches each. Any impostor that slips through marks a hole in the test suite, not in the impostor.

The call

The same 17 impostors are also run against a random suite of equal size — that comparison is what proves the covering array earns its keep.

4 · What the reference bot actually did

The bot gets the enriched text turn by turn. It scored 90.6% across the clean base cases but 49.4% on the messy versions — and this is where the interesting failure lives. A real failure from your run (J009~0001, a different case, but the same shape):

failure_codes : OUTCOME_INCORRECT severity: high factor levels : disfluency=restart · numeric_format=spoken · emotional_frame=skeptical … bot : Before I review account-specific charges, I need to authenticate you. Please tell me the last four digits of your card. user : Hey. I already — sorry, Hey. I already checked my statement this morning. The last agent told me I wouldn't need to verify. Read the failure: the customer did say the digits — but spoken as words (“four eight two one”) inside a sentence that restarts itself, and this keyword-driven bot has no speech-recognition repair and no digit-word parsing, so it never heard them. It never got past authentication, so the whole outcome is wrong. That is a genuine, realistic weakness of the bot under test — exactly what the factory exists to find — and it is not a flaw in the test, because the invariance proof showed the messy text still means PROVIDE_CREDENTIAL(4821).

Two entry points create all of this. The campaign: python run_campaign.py --llm --runs-per-base 1 --out campaign_llm. And the programmatic API, if you want to test your own bot:

from gmsjourney.pipeline import CampaignConfig, run_campaign from gmsjourney.sut.adapter import CallableBotAdapter def factory(tools): # point your bot's tool client at `tools` session = MyBot(tool_client=tools) return CallableBotAdapter(start_fn=session.start, respond_fn=session.respond) run_campaign(CampaignConfig(out_dir="my_bot_run", bot_factory=factory, bot_name="MyBot"))

Glossary

Triple (head / relation / tail)
One fact as three parts, e.g. standard_delivery — has_fee_usd — 0. The whole policy graph is 724 of them.
Meaning card (SemanticFrame)
What a customer turn means, as data: one act plus named slots. Words don’t matter; the card does.
Frame distance
A 0-to-1 number for how far apart two meaning cards are. 0 means identical; 0.75 usually means a hard mismatch such as a different disposition.
Dialog state
Where the conversation is (e.g. ASK_AUTH, PRESENT_TXN, CONFIRM_ACTION). The same words mean different things in different states — “yes” answers whatever was just asked.
ENM (Exact Numeric Memory)
The 12 authoritative numbers (20 turns, 30 days, 4 transactions, $15 fee, 2 attempts…). Read by key, never parsed out of prose.
Cap radius / τ (tau)
Per-relation tolerance in the store’s geometry: how far a true statement may sit from its subject. Forgeries fall outside.
GEODE
The self-correction loop that reviews candidate facts before training. “Converged in 1 iteration” means it found nothing left to fix.
θ (theta)
The runtime plausibility threshold. A tool call scoring above θ is blocked (or, under the quorum rule, sent to review).
Covering array
A small set of test cases that still covers every pair of feature combinations — how 54 journeys stand in for millions.
Closure
Extra cases added until every rule, workflow edge, escalation trigger and boundary has been exercised at least once.
Factor / level
A dial (e.g. noise) and its settings (none, typo, asr). The design assigns levels to bases.
Invariance
The proved claim that an enriched scenario is the same test as its base case: same truth, same meaning per turn, same re-derived outcome.
Negative control
An edit that must be rejected (flip a negation, swap a digit, answer in the wrong state). A checker that accepts these is broken.
Materialised (LLM arm)
A scenario whose LLM-written turns all passed the gates and the proof. Non-materialised scenarios are excluded and counted, never silently dropped.
Pinned utterance
An accepted LLM sentence stored by key, so at run time the bot receives exactly the text that was proved.
Mutant
A deliberately broken copy of the reference bot with one seeded defect, used to measure whether the test suite catches real failures.
Weak link
The first stage in workflow order where a failed run went wrong — the stage the failure is charged to.
Release gate
The final pass/fail verdict, computed from severity tiers and per-tier thresholds. Your run failed it — correctly, since the bot loses half its accuracy under realistic messiness.
