The proof that makes every other number mean something

How Invariance Is Proven

The exact machinery that turns “we tested the bot with messy, realistic sentences” into “we tested the bot with messy sentences that provably mean the same thing as the clean ones” — with a real case walked through end to end.

Everything else in this project rests on one claim. If that claim is false, every failure number is worthless, because you can’t tell whether the bot failed the test or the test failed the bot. This page shows how the claim is established, line by line, using the code in gmsjourney/enrich/invariance.py and evidence from the run in {{CAMPAIGN_DIR}}/.

The claim, stated precisely

For every enriched scenario s′ derived from a base case s: the correct outcome, and the expected behaviour at every stage, are identical to those of s.

“Correct” here is not an opinion. It is whatever the oracle — the program that follows the policy rulebook exactly — produces for the base case. The enriched case must produce the same thing, and the proof must show that the enriched text still carries the base meaning.

There are two ways to lie to yourself when testing a voice bot, and the proof closes both:

  • You changed the answer without noticing. A rephrasing quietly turns “I recognise it” into “I’m not sure I recognise it”, and now the test demands different behaviour. Closure: the intended meaning per turn is fixed before any text exists, and the text must read back to it.
  • Your checker is a rubber stamp. A “grounding check” that accepts anything passes trivially. Closure: the same checker is fed edits that must be rejected — flips, swaps, wrong-state answers — and every one of them has to be caught.

The workflow, step by step

This is InvarianceValidator.prove() and _conclude(), in order. The whole thing runs once per scenario — 85 times in your run.

Replay the base case to get the intended path

base_path(item) runs the oracle on the base spec and records, for every customer turn, the meaning card and the dialog state the turn answers (the bot act that prompted it). Nothing textual survives from here — from now on the proof works on meanings.

for ev in tr.events: if ev["role"] == "bot": last_bot = ev["acts"][-1] elif ev["role"] == "user": path.append((ev["frame"], {"merchant": …, "amount": …})) states.append(_state_of(last_bot))

Realise each turn under the scenario’s factor levels

The realizer writes the messy sentence for turn i using the scenario’s levels (typos, fillers, restarts, spoken numbers…). Each turn gets its own seed, so a retry produces different text rather than the same failure.

text = realizer.realize(frame, scn.factor_levels, seed=f"{sid}|{i}", ctx)

Read it back, in its dialog state

The reader converts the messy sentence into a card, then the ontology canonicalises that card in the state the turn answers. Equivalence requires both: the canonical cards match, and the read card is admissible in that state.

g = reader.read(text, state) ok = ontology.equivalent(frame, g, state) = canonicalize(frame, state) == canonicalize(g, state) AND admissible(g, state)

If it fails, the turn is re-realised with a fresh seed — up to four retries (five realisations). A turn that still fails makes the whole scenario fail L2 and the scenario is rejected and excluded, exactly as GEODE discards questions it cannot vouch for.

L1 — confirm the answer key didn’t drift

The scenario carries its base’s ground truth. The proof re-runs the oracle from scratch and compares content hashes of (answer, per-stage components). This catches any corruption between “the case was generated” and “the case was proved”.

gt_hash(item.answer, item.components) == gt_hash(recomputed.signature(), {f"expected_{k}": v for k, v in recomputed.components().items()})

L3 — replay the read-back cards through the oracle

This is the closing move: the oracle is re-run with frames_override set to the cards that were actually read back from the messy text. Outcome signature and every per-stage component must equal the base’s.

replay = oracle.run(spec, fixture, frames_override=read_frames) oracle_ok = replay.signature() == item.answer and components_match

Why this matters: L2 shows each turn still means the right thing; L3 shows that the sequence of right meanings still produces the right call. An inserted extra turn could pass L2 turn-by-turn and still change the outcome — the signature comparison catches that.

The conversation signature

A hash of (dialog state + canonical card) for every turn, in order. The base conversation and the enriched conversation must produce the same string. This is the machine-checkable form of “same test”, and it is what gets exported as evidence.

sequence_signature(read_frames, states) == sequence_signature(base_frames, states)

L4 — geometric corroboration (reported, not gating)

Two numbers per turn: surface cosine (how far the wording moved — low means the text really is different) and frame distance (0 = identical meaning; 0.5 = a missing or extra slot; 0.75 = a hard mismatch such as a different value; up to 1.0 for a different act or a contradictory value, graded by the store’s tension energy).

L4 never gates. It exists so a reader can see that the accepted scenarios actually exercised the factors — a scenario where every cosine is 1.0 would be a base case in disguise.

Verdict

accepted = L1 ∧ L2 ∧ L3 ∧ signature equality ∧ arm-specific checks. The result object carries every per-turn record, so the verdict can be audited turn by turn rather than trusted.

Why the dialog state is half the proof

The same words mean different things at different moments of the call. “Yes” answers “do you recognise this charge?” with it’s mine; the same “yes” answers “shall I go ahead?” with do it; and “no” to “anything else?” ends the call. A proof that ignored the state would accept nonsense.

So every turn is read in the state it answers, and the policy graph supplies what that state is allowed to hear. Here is the real state context for the case we walk through below:

The other half: proving the checker has teeth

A proof that everything passes is worth nothing unless the same machinery rejects things that should fail. So negative_controls() builds edits that must be caught, sends each through the same reader and ontology, and records three things: was it detected, how far the meaning moved, and — the strongest check — did the oracle’s expected behaviour actually change when the edited card is replayed?

Five families of control:

  • Frame edits — swap the disposition, drop a card request, change a card digit, shift a KB boundary by a day, replace a fake option with a real one.
  • Raw-text edits — flip a negation, transpose card digits, swap “expedited” for “standard”. These are only generated where the sentence carries exactly one cue of that kind, so the edited sentence is a coherent opposite, not a self-contradiction.
  • Wrong state — the same accepted sentence re-read in a state that does not accept its act.
  • Inserted turn — an extra off-task turn, which can pass turn-by-turn checks but changes the conversation signature.
  • Adversarial rewrites (LLM arm only) — DeepSeek is asked to change exactly one meaning element of an accepted sentence; each rewrite must be rejected.

The LLM arm adds a layer on top

When DeepSeek writes the customer turns, the scenario-level proof above is unchanged — the LLM arm is judged by exactly the same L1/L3/signature test, which is what makes the two arms comparable. What the proof does not claim

An honest proof has edges, and they are worth stating plainly:

  • It certifies the customer’s meaning, not the bot’s understanding. A proven scenario says “this text means X”. Whether the bot understands X is exactly what the test then measures.
  • The reader is the instrument, and instruments have error. The reader is deterministic and its sensitivity is measured (433/433 controls, plus a 10,500-sample round-trip stress test in the design notes), but a sentence whose meaning is genuinely ambiguous to a careful human is a limit of any reader.
  • L4 does not gate. Cosine and frame distance are reported as corroboration; the gate is L1/L2/L3 plus signature equality.
  • The two arms are proved to the same standard, but they don’t materialise at the same rate. The template arm proved 85/85 in your run; the LLM arm 29/85. The excluded 56 are a measured property of the arm, listed with their reasons.
  • State-awareness is only as complete as the policy graph. A state that declares the wrong accepted acts would make the proof wrong in the same way — which is why the graph’s consistency with the trained store is itself checked every run.

Running the proof yourself

from gmsjourney.enrich.invariance import InvarianceValidator from gmsjourney.enrich.reader import FrameReader from gmsjourney.enrich.realizers import Realizer from gmsjourney.oracle import PolicyOracle reader = FrameReader(store) realizer = Realizer() oracle = PolicyOracle(store) validator = InvarianceValidator(store, oracle, reader, realizer) proof = validator.prove(scenario) # L1 + L2 + L3 + signatures print(proof.accepted, proof.base_signature == proof.enriched_signature) controls = validator.negative_controls(scenarios, per_type=40) print(controls["_overall"]) # {'n': 433, 'detection_rate': 1.0}

Glossary of the proof’s own vocabulary

Meaning card (semantic frame)
What a turn means, as data: one act plus named slots. The unit the whole proof operates on.
Canonicalise
Normalise a card in its dialog state: aliases to canonical values, bare yes/no to what the state asked, keeping the slot’s own value set.
Admissible
The state accepts this act, every slot is declared for it, and every value belongs to the slot’s value set.
Frame distance
0 identical · 0.5 a missing or extra slot · 0.75 a hard value mismatch · up to 1.0 for a different act or a contradiction graded by the store’s tension energy.
Surface cosine
Embedding similarity between the base and enriched wording. Low means the text really moved; it never gates.
Conversation signature
SHA-256 over the ordered (state, canonical card) pairs, truncated to 20 hex characters. Equal signatures = the same conversation, meaning-wise.
Ground-truth hash
SHA-256 over the oracle’s outcome signature and per-stage components. Equal hashes = the same correct answer.
Re-seed / retry
Re-realising a turn with a fresh seed when the read-back fails (up to four retries), pinning the seed that worked so the run reproduces it.
Negative control
An edit that must be rejected. Its detection rate measures the checker’s sensitivity, not the bot’s behaviour.
Not materialised (LLM arm)
A scenario whose LLM turns could not pass the gates within the attempt budget; excluded and reported with reasons.
